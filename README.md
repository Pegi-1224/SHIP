# SHIP — frontend

SHIP helps women research workplace conditions and compare employers. This repository is the
**frontend only**. It runs today against an in-browser mock API, with clearly marked integration
points for a real backend.

---

## 1. Status: what is real and what is not

| Area | Status |
| --- | --- |
| Company search, profiles, five metric areas, two-company comparison | **Implemented with mocks** |
| Anonymous company-data submissions, editing, 90-day window | **Implemented with mocks** |
| Discussion board: tags, posts, comments, edit/delete | **Implemented with mocks** |
| Onboarding assessment, instruction walkthrough, recommendations | **Implemented with mocks** |
| Anonymous direct messages | **Implemented with mocks**, replies are generated by the mock |
| Authentication, profile, sign-out, account deletion | **Simulated**, see below |
| Real backend integration | **Not implemented** — no backend exists yet |
| Google OAuth, email delivery, analytics, SEO work | **Not implemented** |

**Authentication is simulated.** There is no identity provider and no mail service.
"Continue with Google (mock)" signs you into a fixed demo account without any OAuth flow, and the
email sign-in flow prints the verification code on screen instead of sending it. The UI says so in
two places, and the labels must stay until a real backend replaces them.

**All company data is fictional.** Every company, report, salary figure and post in this build was
invented for the demo (`src/mocks/fixtures/`). Nothing here describes a real employer.

Progress and the next planned step are tracked in [PROGRESS.md](./PROGRESS.md).

## 3. Quick start

```bash
git clone <repository-url>
cd ship-frontend

npm install
cp .env.example .env     # Windows: copy .env.example .env

npm run dev              # http://localhost:5173
```

The app starts in mock mode. No backend, no accounts, no setup. Sign in with any email address —
the verification code appears on screen.

### Demonstration walkthrough

1. Open `http://localhost:5173`. You are signed out: you see a limited preview of recent posts per
   tag, and no search bars (that is the specified rule, not a bug).
2. **Sign up** → tick the eligibility box → enter any email → **Send verification code** → copy the
   6-digit code from the yellow panel → **Verify and continue**.
3. Answer the five assessment questions. The instruction walkthrough opens afterwards.
4. **Companies** → search `Harborline` → open the profile. The salary area shows public data, and
   says the employee-reported average is withheld until five people have contributed.
5. **Share your data** on that salary card → fill the salary section → **Submit**. You are the
   fifth contributor, so the aggregate now appears.
6. **Compare** → pick `Northwind Systems` and `Cobalt Grid Energy`. The summary refuses to rank the
   workforce figures, because one is a global share and the other is a US share.
7. **Discussions** → **New post** → tap another author's avatar to start an anonymous message.
   Send a message containing `!fail` to see the failure-and-retry path.
8. **Profile** → contributions, retake the assessment, reset the demo data, or delete the account.

## 5. Environment configuration

Copy `.env.example` to `.env`. Two variables exist:

```bash
VITE_API_BASE_URL=/api
VITE_ENABLE_MOCKS=true
```

> **Every `VITE_`-prefixed variable is compiled into the JavaScript bundle and is public.** Anyone
> who opens the site can read it. Never put an API key, OAuth client secret, database credential or
> signing key in `.env`.

### Mock mode vs real API mode

| | `VITE_ENABLE_MOCKS=true` (default) | `VITE_ENABLE_MOCKS=false` |
| --- | --- | --- |
| Who answers requests | Mock Service Worker, in the browser | Whatever is at `VITE_API_BASE_URL` |
| Data | Fictional fixtures from `src/mocks/fixtures/` | The backend's real data |
| On failure | A real error state, from the mock's error response | A real error state. **There is no fallback to mock data** |
| Demo banner | Shown | Hidden |

Switching to real API mode is one variable:

```bash
VITE_ENABLE_MOCKS=false
VITE_API_BASE_URL=http://localhost:8000/api
```

MSW is loaded with a dynamic `import()` in `src/main.tsx`, so with mocks disabled the mock backend
and its fixtures are not in the bundle at all. If the real API is unreachable, requests fail and
the UI shows an error with a Retry button. A failed real request is never quietly replaced with a
mock success.

### Does mock data survive a reload?

Yes. The mock database lives in `localStorage` under the key `ship.mock.db`, so a reload keeps your
demo state. It holds fictional demonstration data only. Reset it with **Profile → Demo tools →
Reset demo data**, or from the browser console:

```js
localStorage.removeItem('ship.mock.db'); location.reload();
```

The session token is kept in `sessionStorage` (`ship.session.token`), so closing the tab signs you
out. That is a demo convenience, not a production decision — see
[docs/backend-integration.md](./docs/backend-integration.md).

## 6. Directory structure

```
src/
  app/                  Application shell. Knows about every feature; features never import it back.
    layouts/            AppLayout, Header, MobileNavigation
    providers/          Mantine theme, TanStack Query client, AuthProvider
    router/             Route table and route guards
    App.tsx             Providers + router. Deliberately tiny.
  features/             One folder per product area. Features do not import each other's internals.
    auth/               Sign-in, sign-out, account deletion
    onboarding/         Assessment, instruction walkthrough
    home/               Recommendations and the signed-out preview
    companies/          Search, profiles, submissions, comparison
    discussions/        Feed, posts, comments
    messages/           Conversations
    profile/            Account, contributions, deletion
  shared/               The lowest layer. Must not import from features/ or app/.
    api/                HTTP client, error type, query keys, auth integration point
    config/             Environment, constants, route paths, form option lists
    types/              Domain types used by more than one feature
    ui/                 Presentational components with SHIP behaviour
    utils/              Formatting, statistics, tag rules, text helpers
    styles/             Design tokens and global CSS
  mocks/                The mock backend. Never imported by a page or component.
    fixtures/           Fictional seed data
    handlers/           MSW request handlers, one file per feature
  test/                 Test setup and helpers

docs/                   Architecture, API contract, integration checklist, feature status, open questions
e2e/                    Playwright specs
```

Inside a feature, folders appear **only when needed**:

| Folder | Holds |
| --- | --- |
| `pages/` | Route-level components. One per route. |
| `components/` | UI used by that feature only. |
| `api/` | Functions that call the shared API client. No React. |
| `hooks/` | Queries, mutations, reusable behaviour. |
| `schemas/` | Zod schemas for forms. |
| `types/` | Types used only inside this feature. |
| `index.ts` | The feature's public surface. Other features import only from here. |

Tests sit next to what they test: `comparison.ts` and `comparison.test.ts`.

### Layer rules (enforced by ESLint where possible)

1. **Pages** compose layouts and feature components. They own route params and page-level state.
2. **Components** render and handle interaction. They do not fetch.
3. **Hooks** coordinate fetching, mutations and cache invalidation.
4. **Feature API functions** call the shared client. They never call `fetch` directly.
5. **MSW** intercepts at the network layer. A page must never import a mock fixture.
6. **`shared/` must not import from `features/`.** ESLint fails the build if it does.
7. **Cross-feature imports go through `@/features/<name>`**, never into a subfolder. Also enforced.
8. `App.tsx` stays small. The application does not live there.
9. Domain logic (comparison rules, aggregation, validation) stays out of components.
10. Prefer component state → URL state → TanStack Query → a small Context. There is no Redux/Zustand
    here and none is needed at this size.

## 7. Route table

| Path | Page | Who can open it |
| --- | --- | --- |
| `/` | `HomePage` | Everyone. Signed out shows a limited preview; signed in shows recommendations |
| `/login` | `LoginPage` | Signed-out only. A signed-in user is redirected to `/` |
| `/assessment` | `AssessmentPage` | Signed in. Also used for retaking |
| `/profile` | `ProfilePage` | Signed in. Deliberately **not** behind the assessment gate |
| `/companies` | `CompanySearchPage` | Signed in + assessment finished |
| `/companies/new` | `NewCompanyPage` | Signed in + assessment finished |
| `/companies/:companyId` | `CompanyProfilePage` | Signed in + assessment finished |
| `/companies/:companyId/submit` | `CompanySubmitPage` | Signed in + assessment finished |
| `/compare?a=&b=` | `ComparePage` | Signed in + assessment finished |
| `/discussions` | `DiscussionsPage` | Signed in + assessment finished |
| `/discussions/new` | `NewPostPage` | Signed in + assessment finished |
| `/discussions/:postId` | `PostDetailPage` | Signed in + assessment finished |
| `/discussions/:postId/edit` | `EditPostPage` | Signed in + assessment finished, author only |
| `/messages` | `ConversationListPage` | Signed in + assessment finished |
| `/messages/:conversationId` | `ConversationPage` | Signed in + assessment finished |
| `*` | `NotFoundPage` | Everyone |

Paths are built with helpers in [`src/shared/config/paths.ts`](./src/shared/config/paths.ts) — never
hard-code a URL string.

**Why there is no redirect loop:** `/assessment` is the only destination the assessment gate
redirects to, and that route is not itself gated. `/` is never gated, so a signed-in user who has
not finished the assessment sees a prompt there instead of being bounced.

> **Route guards are navigation, not security.** Everything in this bundle runs on the user's
> machine and can be bypassed. The backend must authorise every request independently: reject reads
> the viewer may not perform, reject writes to records they do not own, and withhold aggregates
> below the privacy threshold. Hiding data the browser already downloaded is not privacy.

## 8. How a request actually flows

Take **"Share your data" on a company page**:

```
1. Button           CompanySubmitPage renders a <form>; SubmitButton is its submit control.
                    src/features/companies/pages/CompanySubmitPage.tsx

2. Validation       react-hook-form + zodResolver run submissionFormSchema. Only the sections the
                    user switched on are validated; errors render under each field and the request
                    is never sent.
                    src/features/companies/schemas/submissionSchema.ts

3. Mutation         useSubmitCompanyData() calls createSubmission or updateSubmission. While it is
                    pending the button is disabled, so a double click cannot submit twice.
                    src/features/companies/hooks/useCompanies.ts

4. API function     createSubmission() builds the path and delegates. No fetch here.
                    src/features/companies/api/companiesApi.ts

5. API client       apiRequest() adds the base URL, JSON headers and the Authorization header,
                    forwards the AbortSignal, and turns any non-2xx into an ApiError.
                    src/shared/api/client.ts

6. Backend / MSW    Mock mode: the handler validates again, enforces the 90-day window, stores the
                    row and persists. Real mode: the actual backend.
                    src/mocks/handlers/companies.ts

7. Cache update     onSuccess invalidates the company detail, the submission eligibility, the
                    contribution history and any open comparison.
                    src/features/companies/hooks/useCompanies.ts

8. UI               TanStack Query refetches the company profile. If this submission was the fifth,
                    the server now returns the aggregate and the page shows it. A success toast
                    fires and the user is navigated back to the profile.
```

The same seven-step shape applies to every mutation in the app.

## 9. How to add things

### Add a page

1. Add the pattern and the builder to `src/shared/config/paths.ts`.
2. Create `src/features/<feature>/pages/MyPage.tsx`. Start with `<PageHeader />` and handle the
   loading / empty / error / unauthenticated states.
3. Export it from `src/features/<feature>/index.ts`.
4. Add the `<Route>` to `src/app/router/AppRoutes.tsx`, inside the right guard.
5. Add a row to the route table in section 7 of this README.

### Add an API endpoint

1. Agree the contract and write it into [`docs/api-contract.md`](./docs/api-contract.md), marked
   **Proposed** until the backend confirms it.
2. Add the request/response types to `src/shared/types/` (cross-feature) or the feature's `types/`.
3. Add the function to `src/features/<feature>/api/`, using `api.get` / `api.post` / … and
   forwarding `signal`.
4. Add a query key to `src/shared/api/queryKeys.ts`.
5. Add the hook in `src/features/<feature>/hooks/`, including what a mutation invalidates.
6. Add the mock handler (next section) so the app still runs.

### Add a mock handler

1. Open `src/mocks/handlers/<feature>.ts`.
2. Add `http.get(url('/your/path'), async ({ request, params }) => { … })`.
   - `url()` prefixes the configured base path.
   - `currentUser(request)` resolves the session; answer `unauthorized()` when it returns null.
   - Mutate `db()` and call `persist()` so the change survives a reload.
   - Use the shared `validationError` / `notFound` / `conflict` helpers so the error envelope
     matches the real contract.
3. Literal routes must be registered **before** parameterised ones (`/companies/compare` before
   `/companies/:companyId`).
4. Add a test. `src/test/signIn.ts` signs a test in without driving the UI.

## 10. Worked example: the privacy threshold

The clearest end-to-end example in the codebase. A company's employee-reported numbers only appear
once five distinct people have contributed (spec 3.5, 6.2, AC-6).

| Step | File |
| --- | --- |
| The constant, used for copy and defensive rendering | [`src/shared/config/constants.ts`](./src/shared/config/constants.ts) |
| The envelope type: `summary` is `null` below the threshold | [`src/shared/types/company.ts`](./src/shared/types/company.ts) (`UserReportedMetric`) |
| The rule, applied server-side so the numbers never reach the browser | [`src/mocks/aggregations.ts`](./src/mocks/aggregations.ts) (`withThreshold`) |
| Its tests, including dropping back below the threshold after a deletion | [`src/mocks/aggregations.test.ts`](./src/mocks/aggregations.test.ts) |
| The endpoint that serialises it | [`src/mocks/handlers/companies.ts`](./src/mocks/handlers/companies.ts) |
| The hook that refetches after a submission | [`src/features/companies/hooks/useCompanies.ts`](./src/features/companies/hooks/useCompanies.ts) |
| The UI: aggregate, or an explanation of why it is withheld | [`src/features/companies/components/metrics/CompanyMetrics.tsx`](./src/features/companies/components/metrics/CompanyMetrics.tsx) and [`ThresholdNotice`](./src/shared/ui/data-display/DataPoint.tsx) |
| The integration test for the whole journey | [`src/features/companies/pages/CompanyProfilePage.test.tsx`](./src/features/companies/pages/CompanyProfilePage.test.tsx) |
| The browser check | [`e2e/critical-flows.spec.ts`](./e2e/critical-flows.spec.ts) |

The point to carry into the backend work: **the threshold is enforced where the data is assembled.**
The frontend renders what it was given. If the API ever returned a hidden aggregate, the privacy
promise would already be broken, whatever the UI did with it.

## 11. Conventions

**Naming**

- Components and their files: `PascalCase.tsx` (`CompanyCard.tsx`).
- Hooks: `useThing.ts`, exported as `useThing`.
- API functions: verb first — `fetchCompanyProfile`, `createSubmission`.
- Types and interfaces: `PascalCase`. No `I` prefix.
- Constants: `SCREAMING_SNAKE_CASE`.
- CSS Modules: `Component.module.css` next to the component; class names are `camelCase`.

**Imports**

- Absolute `@/…` for anything outside the current feature; relative `./` or `../` inside it.
- Cross-feature: `@/features/companies`, never `@/features/companies/api/companiesApi`.
- Shared UI: `@/shared/ui`.
- Type-only imports use `import type`. ESLint enforces it.
- Order: node/externals → `@/shared` → `@/app` → `@/features` → relative → CSS.

**Components**

- Reuse what is in `@/shared/ui` before writing something new.
- Use Mantine primitives directly when they fit. Wrap one only to add SHIP behaviour or policy.
- Custom styling goes in a CSS Module reading the tokens in `src/shared/styles/tokens.css`. No
  hard-coded colours or pixel spacing.
- Every page handles loading, empty, error-with-retry and unauthenticated. `QueryStateView` does all
  four when a region depends on one query.
- Every visible button navigates, submits, opens a dialog, or is disabled with a stated reason.

**Accessibility (not optional)**

- Every input has a label. Hide it visually with `labelProps={{ className: 'ship-visually-hidden' }}`
  if the design calls for it, but never remove it.
- Never remove the focus ring without an equally visible replacement.
- Charts are `aria-hidden` and always paired with a table carrying the same numbers.
- Do not convey meaning with colour alone.

## 13. Hosting

This is a single-page app. **The host must serve `index.html` for every path it does not recognise
as a file.** Without that, a visitor who refreshes on `/companies/northwind-systems` gets a 404
from the host, even though the route exists.

| Host | What to configure |
| --- | --- |
| Netlify | `public/_redirects` containing `/*  /index.html  200` |
| Vercel | `vercel.json` → `{ "rewrites": [{ "source": "/(.*)", "destination": "/index.html" }] }` |
| Nginx | `location / { try_files $uri $uri/ /index.html; }` |
| S3 + CloudFront | Error document `index.html`, 404 and 403 both rewritten to `/index.html` with status 200 |
| GitHub Pages | Needs a `404.html` copy of `index.html`; also set Vite's `base` |

Build with `npm run build` and deploy `dist/`. Set `VITE_API_BASE_URL` and `VITE_ENABLE_MOCKS` in
the host's build environment — they are read at **build** time, not at runtime, so changing them
requires a rebuild.

Deploying with `VITE_ENABLE_MOCKS=true` publishes the demo, including `public/mockServiceWorker.js`.
That is fine for a review build and wrong for production.

## 14. Troubleshooting

| Symptom | Cause and fix |
| --- | --- |
| Every request fails right after `npm run dev` | The service worker had not started. Hard-reload once. If it persists, re-run `npx msw init public/ --save`. |
| Changes to `src/mocks/fixtures/` do nothing | The saved mock database wins. Profile → Reset demo data, or `localStorage.removeItem('ship.mock.db')`. |
| Signed out after every reload | Expected: the token lives in `sessionStorage`. Closing the tab ends the session. |
| 404 on refresh in production | The host is not falling back to `index.html`. See section 13. |
| `npm test` fails with `document.fonts is undefined` | `src/test/setup.ts` is not loading. Check `setupFiles` in `vite.config.ts`. |
| `npm run e2e` cannot find a browser | Run `npm run e2e:install` once. |
| `EBADENGINE` on install | Your Node version is below the range in section 2. |
| ESLint: *"is restricted from being used by a pattern"* | A cross-feature deep import. Export it from that feature's `index.ts` and import `@/features/<name>`. |
| Real API mode returns 404s for everything | `VITE_API_BASE_URL` is wrong, or the backend has not implemented that path yet. Check the Network tab against `docs/api-contract.md`. |

## 15. Known limitations and unresolved requirements

**Simulated, not integrated**

- Google sign-in runs no OAuth flow.
- No email is sent; the mock returns the verification code in the response body.
- The session token is an unsigned opaque string in `sessionStorage`.
- Direct-message replies are generated by the mock after a short delay. There is no second person,
  no WebSocket and no push transport.
- Banned-word filtering for tags and company names uses a tiny placeholder list in the client. The
  real list is the backend's.

**Not implemented**

- Pagination controls. The API and the client support `page` / `pageSize`, but no list has a
  "load more" control yet; everything shows the first page.
- Analytics events (spec 7.2). None are emitted.
- SEO work (spec 8.2). The app is client-rendered with one static `<title>`.
- Cookie consent notice (spec 9).
- Report/abuse flows and an admin console (explicitly out of scope in spec 1.4).

**Open questions for the team** — all recorded with context in
[docs/decisions-and-questions.md](./docs/decisions-and-questions.md):

- **Password changes (DQ-01).** Spec 3.6 lists "password change" on the Profile page, but spec 3.2
  specifies passwordless sign-in. No password exists to change. The Profile page states this; no
  password system was invented. **Needs a product decision.**
- **Benefits comparison (DQ-04).** The spec's worked example counts benefits as an area a company
  can "lead" in. We describe the difference instead, because a longer published list is not evidence
  of a better employer. **Needs confirmation.**
- **Reporting-period mismatches (DQ-03).** We refuse to compare measured statistics across different
  periods, but allow it for current policies. **Needs confirmation.**
- **Priority-to-tag mapping (DQ-05).** Assessment question 3 is not a tag question, so we map each
  priority onto tags. The mapping is a product decision.
- **Missing task schedule.** The schedule referenced in the brief was not supplied. The
  implementation order came from the brief itself. **Please send it so we can reconcile.**
- **Only one design asset.** The single supplied design is a hand sketch of the comparison page.
  Everything else follows a design system we chose and documented. **Needs design review.**
